## Review 结论

### 本轮重连故障定位与修复

- 用户反馈持续 RECONNECTING。设置菜单操作已被串口确认，模式保存为 RADIO，重启自动恢复；Wi-Fi 取得 IP，电台返回 HTTP 200。
- 原 96 KiB LVGL 池实测 UI 峰值 13,560 字节，连接后流缓冲分配完成时堆仅 18,212 字节；MP3 首帧初始化返回 -2（ESP_AUDIO_ERR_MEM_LACK）。原逻辑漏传该错误，导致持续重试。
- 将 LVGL 池改为 64 KiB，给系统释放 32 KiB，MP3 解码通过。继续发现全双工 I2S 的 RX DMA 分配失败；电台改用仅 TX/DAC 的 BSP 入口，原全双工接口保留。随后设备成功打开 44,100 Hz/16-bit/单声道输出并写入 PCM，起播堆 12,696 字节，最大连续块 7,680 字节，任务栈余量 3,276 字节。
- 还修复了将 HTTP EAGAIN 短暂超时当成永久断流的问题：保留半帧，连续 10 秒无新数据才重新连接；单次读取仍为 1.5 秒，方便及时取消。新增读取/解码/音频错误日志和每 30 秒播放内存日志。
- 上述属于串口和代码证据；声音、短暂超时修复后的连续播放仍以最新实机结果为准，不能据此宣称长期稳定。

用户反馈的“长按 OK 后卡 NERV”经确认短按 OK 能返回，原因为旧待机入口没有提示，未观察到该操作触发重启。当前已按用户的新要求改成长按 OK 设置菜单，不再经过 NERV 待机。首页电台配网也已改为独立面板，内嵌扫描选网表单。

分区不兼容和正式素材缺失已通过本次全新安装解决。代码采用本地音频退出后再启动电台、取消网络任务后再恢复本地的串行资源交接，AP/STA 入口互斥。当前主机测试没有执行真实 FreeRTOS/Wi-Fi/MP3 任务生命周期，模型单测不能替代设备验收。Wi-Fi 与 MP3 的运行内存仍是重点验收项，不能因构建通过就认定电台稳定。杭州台名存在来源冲突，需听音核对。

## 原播放器框架与 TCP 窗口对照

- 按用户要求，电台页改为共用原播放器的顶栏、电量框和矩形面板，使用相同中央仪表区、台名区与四格控制条。用户确认界面符合要求。
- 为测试旧 2880 字节 TCP 接收窗口的吞吐限制，将窗口扩大为 11520 字节、接收队列 10；LVGL 池从 64 KiB 调整为 48 KiB，为网络释放 16 KiB。实机中文界面峰值 19780 字节、稳定占用约 16208 字节；未发现分配失败。
- 扩大窗口仍未解决卡顿。station=3 在 25796 ms 内收到 26819 字节、输出 3343 ms PCM，用户确认仍卡顿或重连。不能将本次窗口试验记为稳定性修复。
- 继续增加 TCP 接收现场诊断，区分窗口耗尽、乱序等待和上游无数据；该诊断在 lwIP 线程内只读 PCB，不更改连接。
